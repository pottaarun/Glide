# Setup & configuration

How to run Glide locally, every configuration knob, and how to deploy. For how
the pieces fit together, see [Architecture](./architecture.md).

## Prerequisites

- **Node.js `^22.18.0` or `>=24.11.0`** and npm (also pinned in `.nvmrc`).
- A **Cloudflare account** with **Workers AI** enabled.
- A **Cloudflare Zero Trust organization** and a self-hosted **Access application**
  for the complete production hostname.
- **[Wrangler](https://developers.cloudflare.com/workers/wrangler/)** — installed
  as a dev dependency, so `npx wrangler` / the npm scripts work out of the box.
- A **Cloudflare API token** — create one at
  [dash.cloudflare.com/profile/api-tokens](https://dash.cloudflare.com/profile/api-tokens).
- A **[Vectorize](https://developers.cloudflare.com/vectorize/) index** named
  `glide-guidance` for team-guidance RAG (create it once — see
  [The `VECTORIZE` binding](#the-vectorize-binding-team-guidance-rag)). Optional
  for local dev: without it, guidance falls back to injecting all enabled docs.
- _Optional:_ a running [Switchflare](https://developers.cloudflare.com/)
  migration-tool Worker for the provider-migration features.

## Quick start (local development)

```bash
# 1. Install dependencies
npm install

# 2. Configure local secrets and a loopback-only development identity
cp .dev.vars.example .dev.vars
#   then edit .dev.vars; set GLIDE_TOKEN_KEY and GLIDE_DEV_ACCESS_EMAIL

# 3. Build the client bundle the Worker serves from ./dist/client
npm run build

# 4. Run the Worker locally (serves the SPA + the GlideAgent Durable Object)
npm run dev
```

Open the loopback URL Wrangler prints. `GLIDE_DEV_ACCESS_EMAIL` supplies the local
identity because localhost has no Access edge to inject a JWT. Use an
`@cloudflare.com` test address to create rooms. The bypass is ignored for every
non-loopback request URL. Keep Wrangler bound to loopback and do not expose this
development server through a LAN listener or reverse proxy.

> Set `GLIDE_TOKEN_KEY`, then enter a Cloudflare API token directly into the GUI
> (**Connection → Set token**); it's stored encrypted in the Durable Object. See
> [Security model](./security.md). Never put a token in the chat composer.

## Configuration

### Non-secret vars (`wrangler.jsonc`)

| Var | Default | Purpose |
| --- | --- | --- |
| `GLIDE_MODEL` | `@cf/openai/gpt-oss-120b` | The Workers AI model that powers the chat brain. Full-precision, 128k context, reliable function calling. (gpt-oss is non-streaming on Workers AI; `workers-ai-provider` synthesizes the stream — see [Architecture](./architecture.md#the-chat-turn-lifecycle).) |
| `GLIDE_EMBED_MODEL` | `@cf/baai/bge-base-en-v1.5` | The Workers AI embedding model for **both** team-guidance and Cloudflare-docs RAG. Its output dimensionality (768) **must** match the `glide-guidance` Vectorize index. |

### Cloudflare Access and room membership

Production Glide requires Cloudflare Access at the edge and validates the Access
application token again inside the Worker. Configure it before exposing this
version:

1. Create a self-hosted Access application covering the Worker's complete
   production hostname. Protect all paths, including static assets, `/api/*`, and
   `/agents/*`; do not create an Agent-only application.
2. Enable the organization identity provider and/or One-time PIN. The Access Allow
   policy may admit prospective invitees broadly because it authenticates identity;
   Glide's durable room ACL performs the per-room authorization.
3. Copy the application's **Application Audience (AUD) Tag** to `POLICY_AUD` and
   the standard `https://<team>.cloudflareaccess.com` team URL to `TEAM_DOMAIN`.
4. Set both values on the Worker, then verify `/api/session` returns the canonical
   signed-in email. Do not use `GLIDE_DEV_ACCESS_EMAIL` on the deployed Worker.

`src/access-auth.ts` verifies the `Cf-Access-Jwt-Assertion` signature through the
team JWKS, restricts algorithms to RS256, and checks issuer, audience, `type: app`,
email, non-empty subject, and expiry. Identity service tokens have no email and an
empty subject, so they are rejected. Missing production configuration returns
`503`; a missing assertion returns `401`; an invalid or expired assertion returns
`403`. The issuer-scoped remote-JWKS resolver is reused in memory. Key-endpoint
timeouts, network/HTTP failures, and malformed key sets return no-store
`503 access_keys_unavailable` with `Retry-After: 10`; unknown key ids remain
`403 access_token_invalid`.

Room authorization is independent of the URL:

- `POST /api/room-access` is the only creation/claim path. It requires an exact
  same-origin `Origin`; Agent routing performs read-only admission and cannot
  activate a room. The admin and transient-close checks add `intent=inspect`, which
  performs only read-only membership authorization.
- New room ids match `^[A-Za-z0-9_-]{1,128}$` and reserve `__system__` (docs-index
  coordinator) and `__registry__` (room registry); the default
  is a 32-character hyphenless UUIDv4. Existing non-control ids up to 200
  characters are lookup-only and cannot create empty rooms. The browser and API
  share a PartySocket-compatible mapping from that display id to a serialized
  Durable Object name capped at 1,024 bytes.
- An exact canonical `@cloudflare.com` identity can create a canonical empty room.
- The first Cloudflare employee to open an existing legacy room becomes its owner.
  Old invitation records remain audit-only and every guest must be re-invited.
- Every other identity needs an existing `glide_room_members` row for that room.
- Verified Cloudflare employees can list all rooms via `GET /api/rooms` (the admin
  **All rooms** view). This is a convenience index only; entering any listed room
  still requires a `glide_room_members` row. The room owner can permanently delete
  a room (`destroyRoom`, confirmed with `DELETE THIS ROOM`); any member can set a
  display-only room name.
- Any current member can invite another canonical email, up to 100 members. The
  ACL grant and `glide_room_invites` audit write are atomic, but the recipient must
  authenticate as that exact address.
- Only the owner can remove a non-owner. Removal immediately closes all matching
  sockets with code `1008`.
- Agent WebSockets require the exact application origin. Initial protocol frames
  are suppressed before admission; the Durable Object repeats membership/expiry
  checks before every frame.
- Every accepted connection gets a durable expiry schedule that survives
  hibernation and closes idle expired sessions with `1008`. Scheduling failure
  closes with `1011`; normal close cancels the schedule.
- A previously absent room remains provisional until owner activation. Denied
  probes schedule idempotent destruction; schedule-write failures get bounded
  retries and then arm a native fallback alarm so destruction has a fresh
  invocation. Cleanup preserves any room that gained a member or durable data,
  then uses one atomic `deleteAll()` without a persistent condemned marker.
  Activation removes the marker atomically and retries once with an idempotency
  record if cleanup reset the object during the request.

The browser reads `/api/session` and `/api/room-access` through a 128,000-byte
response ceiling and 15-second request deadline. Worker-served HTML denies framing with CSP `frame-ancestors
'none'` and `X-Frame-Options: DENY`.

`GLIDE_DEV_ACCESS_EMAIL` is a deliberate local testing seam. It is accepted only
when `request.url` has a loopback hostname (`localhost`, `*.localhost`,
`127.0.0.1`, or `::1`) and is ignored on production hostnames even if accidentally
configured. The request URL cannot prove the network peer is local, so do not run
Wrangler with a non-loopback bind address or proxy this bypass to another host.

### Workers Rate Limiting bindings

Authenticated Glide traffic is protected by two
[Workers Rate Limiting](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/)
bindings in `wrangler.jsonc`:

```jsonc
"ratelimits": [
  {
    "name": "AGENT_RATE_LIMITER",
    "namespace_id": "2026072901",
    "simple": { "limit": 120, "period": 60 }
  },
  {
    "name": "CHAT_RATE_LIMITER",
    "namespace_id": "2026072902",
    "simple": { "limit": 20, "period": 60 }
  }
]
```

| Binding | Key and call site | Limit |
| --- | --- | --- |
| `AGENT_RATE_LIMITER` | A SHA-256 digest of Cloudflare's `CF-Connecting-IP` for each dynamic HTTP request that requires authentication, including root/session/room checks, Agent handshakes, and `/get-messages`. | 120 requests per 60 seconds. |
| `AGENT_RATE_LIMITER` | A `protocol:` bucket derived from the verified Access subject for every inbound WebSocket frame before RPC/chat dispatch. | 120 frames per 60 seconds per authenticated identity. |
| `CHAT_RATE_LIMITER` | A `chat-client:` bucket derived from the verified Access subject, checked after chat validation but before persistence. Selected expensive RPCs use the same budget. | 20 chat submissions/expensive operations per 60 seconds across that identity's rooms. |
| `CHAT_RATE_LIMITER` | A `chat-room:` bucket keyed by a SHA-256 digest of the room name, checked only after the identity bucket passes. | 20 chat submissions/expensive operations per 60 seconds across everyone in that room. |

The raw IP, Access subject, and room name are never used as log fields or plaintext
rate-limit keys. There is no trusted `X-Forwarded-For` fallback: on Cloudflare's network,
`CF-Connecting-IP` is authoritative; a local request without it enters one shared
`unidentified` HTTP bucket. After JWT verification, the Worker overwrites an
internal `X-Glide-Client-Rate-Key` header with a digest of the verified Access subject. The Durable Object
accepts only the exact digest shape and persists that opaque value in connection
state, so neither the raw IP nor subject is forwarded into hibernation state.
Structured events correlate a room with its opaque Durable Object id instead of
the display/storage name.
Hashed JS/CSS and non-root SPA/admin asset requests do not call either binding;
the authenticated root document does consume `AGENT_RATE_LIMITER`.

An exhausted HTTP bucket returns JSON `429`, `Cache-Control: no-store`, and
`Retry-After: 60`. If a binding call itself fails, dynamic authenticated HTTP traffic
fails closed with JSON `503` and `Retry-After: 10`. Protocol exhaustion closes
the WebSocket with code `1013`; chat exhaustion returns a bounded chat error before
the user turn can persist. The React client preserves/rechecks delivery rather
than treating a rejected turn as delivered.

`namespace_id` is an account-global positive-integer string. Keep these IDs unique
if other Workers in the same account define rate-limit bindings; deliberately
reusing one shares counters for identical keys. Changing an ID starts a distinct
counter namespace. If you tune a limit, update `wrangler.jsonc`,
`wrangler.test.jsonc`, the policy constants in `src/rate-limits.ts`, and the docs,
then run `npm run types`, `npm run check`, and `npm test`.

Cloudflare's counters are permissive, eventually consistent, and local to the
Cloudflare location handling the call. They reduce abuse; they are not exact
accounting and do not replace Access or room membership. Network identity can group
people behind a corporate/mobile NAT during HTTP admission and can be bypassed by a
source that rotates IPs. Once authenticated, protocol and chat limits use the
verified Access subject, while the room bucket bounds aggregate AI use.
Local development uses a local simulation and does not share production counters;
the regression suite injects deterministic allow/deny outcomes for enforcement
branches.

### Secrets / environment

Set these via `.dev.vars` locally or `wrangler secret put <NAME>` in production.
They're declared for TypeScript in `src/env.d.ts`.

| Name | Required | Purpose |
| --- | --- | --- |
| `TEAM_DOMAIN` | Production | Canonical Access team URL used as the expected JWT issuer and JWKS origin. |
| `POLICY_AUD` | Production | Audience tag of the Access application protecting this deployment. |
| `GLIDE_DEV_ACCESS_EMAIL` | Local only | Explicit identity for loopback Wrangler requests. Ignored on deployed hostnames. |
| `GLIDE_TOKEN_KEY` | Required for Cloudflare API access | Key used to derive the AES-256-GCM key that encrypts GUI-provided tokens at rest. **Without it, GUI token storage is disabled.** Generate one with e.g. `openssl rand -base64 32`. |
| `MIGRATION_API_URL` | Optional | Base URL of the Switchflare / migration tool Worker. Used as a fallback when the `MIGRATION` service binding isn't present. |

Each room can use only the token entered in that room. `GlideAgent.getToken()`
decrypts it with `GLIDE_TOKEN_KEY`; if the key is absent, rotated, or the
ciphertext is corrupt, token access fails closed and the room must re-enter it.
There is no deployment-wide Cloudflare API token fallback. This partitions
credentials by room. Access identity and `glide_room_members` separately ensure
that obtaining a token-bearing room URL does not grant use of its credential.

### Upgrading from `CF_API_TOKEN`

Older deployments could use one Worker-wide `CF_API_TOKEN`. Current Glide never
reads that binding, and Worker secrets are not retrievable in plaintext. Migrate
deliberately instead of assuming existing rooms inherited the old credential:

1. Set a strong `GLIDE_TOKEN_KEY` with `npx wrangler secret put GLIDE_TOKEN_KEY`,
   then deploy the current code.
2. Create a least-privilege Cloudflare API token for each sensitive room (or use
   the original value from your secure credential store) and enter it through
   **Connection → Set token**. Do not put it in `.dev.vars` or chat.
3. In every room that must keep API access, confirm the token badge and run an
   intended read such as account/zone discovery. A green badge proves
   authentication, not every product permission.
4. Confirm no room depends on the Worker-wide secret, then remove it with
   `npx wrangler secret delete CF_API_TOKEN`. Wrangler immediately deploys a new
   Worker version when deleting a secret.
5. Revoke the former Cloudflare token after every room using that value has moved
   to a replacement. Deleting the Worker secret does not revoke the API token.

### The `VECTORIZE` binding (team-guidance RAG)

`wrangler.jsonc` declares a [Vectorize](https://developers.cloudflare.com/vectorize/)
binding for the team-guidance retrieval described in
[Architecture → Team guidance](./architecture.md#team-guidance-rag--srcguidance-ragts):

```jsonc
"vectorize": [{ "binding": "VECTORIZE", "index_name": "glide-guidance" }]
```

Create the index once, before your first deploy. Its dimensions and metric must
match `GLIDE_EMBED_MODEL` (`@cf/baai/bge-base-en-v1.5` → **768 dims**, cosine):

```bash
npx wrangler vectorize create glide-guidance --dimensions=768 --metric=cosine
```

> **Optional but recommended.** If the binding or index is absent, guidance still
> works: Glide falls back to injecting **all enabled** guidance docs into the
> prompt (every Vectorize/AI call is wrapped in try/catch and degrades quietly).
> RAG only kicks in once a room has more than `GUIDANCE_INJECT_ALL_MAX` (6)
> enabled docs, so small teams may never need the index. For local `wrangler dev`
> you can skip it entirely.

If you change `GLIDE_EMBED_MODEL` to a model with a different output size, delete
and recreate the index with matching `--dimensions`, then re-embed existing docs
from the admin dashboard (**Team guidance → Reindex**).

### Cloudflare-docs RAG & the weekly cron

The same `VECTORIZE` index also backs the **Cloudflare-docs RAG** (a shared
`__cfdocs_v2__` namespace, separate from the per-room guidance keys). See
[Architecture → Cloudflare-docs RAG](./architecture.md#cloudflare-docs-rag--srcdocs-scraperts).

- **It is populated and refreshed automatically.** `wrangler.jsonc` declares a cron trigger,
  `"triggers": { "crons": ["0 2 * * SUN"] }`, so the Worker's `scheduled()` handler
  runs the reindex every Sunday at 02:00 UTC through one fixed internal Durable
  Object. The first GET of `/` also asks that same system object to bootstrap an
  empty index, so a new deployment does not wait until Sunday. Cron triggers run
  only on deployed Workers unless tested through Wrangler's scheduled-test route.
- **It is not room-admin controlled.** Room clients expose no start, cancel, or
  clear RPC controls, and public HTTP/WebSocket routes to the reserved coordinator
  return `404`. Refreshes update successful pages in place, retain last-known-good
  vectors for failed pages, and delete removed pages only after all product indexes
  were enumerated successfully. Startup reconciliation re-arms a lost delayed tick
  only after the durable queue-ready handoff completed.
- **Optional.** Without the `VECTORIZE` binding the feature is inert — chat still
  works, it just won't cite the docs.

### The `MIGRATION` service binding

`wrangler.jsonc` can declare a service binding to a Worker named `switchflare`. It
is **commented out by default** so a fresh `wrangler deploy` succeeds without a
migration Worker in your account:

```jsonc
// "services": [{ "binding": "MIGRATION", "service": "switchflare" }]
```

Uncomment it to invoke the migration tool directly inside the runtime, which works
even when its public hostname is behind Cloudflare Access. It is **preferred** over
`MIGRATION_API_URL` (`src/migration.ts`).

> **Note:** If you uncomment this block but don't have a `switchflare` Worker
> deployed in your account, `wrangler deploy` will fail on the binding. Either
> deploy/point at your own migration Worker, leave the block commented out, or set
> `MIGRATION_API_URL` instead. With neither configured, the migration features are
> simply disabled and the tools explain how to enable them — the rest of Glide
> works.

For local development against a migration tool you run yourself, start it with
`wrangler dev` and point `MIGRATION_API_URL` at its origin (e.g.
`http://localhost:8788`).

### Cloudflare API token permissions

Reads and writes require matching token permissions. When an API call fails with
a permission error, Glide suggests the likely read/write permission group from
`PERMISSION_MAP` in `src/cf-api.ts`. Verify it against Cloudflare's current API
token permission list and scope it to only the required account/zones:

| API path contains | Permission to grant |
| --- | --- |
| `GET /zones` | Zone > Zone > Read, scoped to the zones Glide must discover. |
| `POST /zones` | Zone > Zone > Edit, scoped to **All zones/domains**. For Account API Tokens, use a separate zone/domain-scoped policy; this permission is not shown under **Entire Account**. |
| `/dns_records` | DNS Read for GET; DNS Edit for writes (Zone) |
| `/settings/` | Zone Settings Read for GET; Zone Settings Edit for writes (Zone) |
| `/rulesets` | Zone WAF or Account Rulesets, Read for GET and Edit for writes |
| `/rules/lists` | Account Filter Lists, Read for GET and Edit for writes (Account) |
| `/load_balancers` | Load Balancers, Read for GET and Edit for writes (Zone) |
| `/load_balancers/pools` | Load Balancing: Monitors and Pools, Read for GET and Edit for writes (Account) |
| `/gateway/rules` | Zero Trust: Gateway, Read for GET and Edit for writes (Account) |
| `/access/apps` | Access: Apps and Policies, Read for GET and Edit for writes |
| `/cfd_tunnel` | Cloudflare Tunnel, Read for GET and Edit for writes (Account) |
| `/teamnet/routes` | Cloudflare Tunnel: Routes, Read for GET and Edit for writes (Account) |
| `/workers/scripts` | Workers Scripts — Edit (Account) |

Prefer a distinct token per sensitive room, scoped to only the accounts, zones,
and product permissions that room needs. Avoid sharing one broad token across
unrelated rooms. The new-zone exception below needs Zone Edit over all zones, but
does not justify broad unrelated account permissions.

`setCloudflareToken` first calls the
user-scoped `/user/tokens/verify` endpoint. Because that endpoint can return
401/403 for a valid account-scoped token, Glide then tries authenticated
`/accounts` and `/zones` reads. The token is marked unverified only when the
verify endpoint and both read fallbacks fail. A room that reconnects with a stored
unverified token calls `reverifyToken` once so old false negatives self-correct.

Verification proves authentication, not complete authorization. A green badge can
still be followed by a permission-specific failure when a later operation reaches
a product or scope the token cannot access.

Zone creation has a special resource-scope requirement: a domain that does not
exist yet cannot be selected as a specific-zone resource. For an **Account API
Token**, add a zone/domain-scoped policy covering **All zones/domains**, then grant
**DNS & Zones > Zone > Edit**; do not put that permission under an **Entire
Account** policy. For a user API token, grant **Zone > Zone > Edit** with Zone
Resources set to **All zones**. Keep the separate account/product permissions as
narrow as the workflow permits.

When the room has a token, `add_domain` performs an exact, account-filtered zone
lookup before it queues `POST /zones`. If the zone exists, Glide selects it as the
room default and moves to DNS review. Without a token, an explicit account id can
still produce an approval for later Apply; a matching selected default without an
explicit account is blocked until Glide can verify it. In every case, a matching
pending, applying, or failed approval is reused. Generic `cf_write` cannot bypass
the dedicated zone-creation path.

## Deploying

```bash
# Create the guidance Vectorize index (once, recommended)
npx wrangler vectorize create glide-guidance --dimensions=768 --metric=cosine

# Set production secrets (once)
wrangler secret put TEAM_DOMAIN          # Access issuer / team URL
wrangler secret put POLICY_AUD           # Access application audience
wrangler secret put GLIDE_TOKEN_KEY      # enables encrypted per-room token storage
wrangler secret put MIGRATION_API_URL    # optional, if not using the service binding

# Build + deploy
npm run deploy
```

Create and enable the full-hostname Access application before exposing the new
Worker version. The Worker serves the built SPA from `./dist/client` via the
`ASSETS` binding and routes authorized `/agents/*` traffic to the `GlideAgent`
Durable Object. `observability` is enabled
in `wrangler.jsonc`, so Worker logs/metrics are available in **Workers & Pages →
glide → Observability → Logs** and through `npx wrangler tail glide`. Wrangler
deploys the `AGENT_RATE_LIMITER` and `CHAT_RATE_LIMITER` configurations with the
Worker; no separate dashboard WAF rule is required.

A deploy can evict or restart the room Durable Object during an active turn. Avoid
deploying during live conversations when possible. After a deploy, wait for the
room's **live** badge or hard-refresh before sending another message.

### Deploy checklist

- [ ] Full production hostname is protected by a Cloudflare Access application;
      its policy supports the intended IdP and/or One-time PIN invitees.
- [ ] `TEAM_DOMAIN` and `POLICY_AUD` match that application, `/api/session`
      returns the signed-in canonical email, and `GLIDE_DEV_ACCESS_EMAIL` is not
      configured on production.
- [ ] `GLIDE_TOKEN_KEY` set so teams can enter encrypted per-room tokens in the GUI.
- [ ] `glide-guidance` Vectorize index created (768 dims, cosine) — or you accept
      guidance running in inject-all fallback mode.
- [ ] `MIGRATION` `services` block left commented out, **or** it points at a real
      Worker, **or** `MIGRATION_API_URL` is set, **or** you accept migration
      features being disabled.
- [ ] Rate-limit namespace IDs are unique within the account and the 120/minute
      Agent plus 20/minute chat thresholds fit expected team traffic.
- [ ] `npm run check` passes.
- [ ] `npm test` passes.
- [ ] `npm run build` passes (the known large-chunk advisory is non-fatal).
- [ ] `npx wrangler deploy --dry-run` passes before the production deploy.
- [ ] Workers AI is enabled on the account and both `GLIDE_MODEL` and
      `GLIDE_EMBED_MODEL` are models you can access.
- [ ] The weekly Cloudflare-docs cron is present if shared docs grounding is desired.
- [ ] Open `/` once after the first deploy (or wait for cron) to bootstrap the
      shared docs index; search remains best-effort while the background crawl runs.

## Troubleshooting

- **The room says reconnecting:** keep the draft in the composer and wait for
  **live**. Hard-refresh if the socket does not recover after a deployment.
- **Agent requests return `429` or chat reports too many messages:** stop manual
  retries for about one minute. A protocol-frame limit closes the socket with
  `1013`, so let the normal reconnect settle before sending again.
- **Agent requests return `503` with `rate_limit_unavailable`:** abuse protection
  failed closed. Retry after 10 seconds; if it persists, inspect
  `rate_limit.unavailable` in Workers Observability and verify both bindings are
  present on the active deployment.
- **The app returns `503` with `access_not_configured`:** set `TEAM_DOMAIN` and
  `POLICY_AUD` from the Access application on the active Worker version.
- **The app returns `401`/`403` before the room opens:** complete the Access login,
  confirm the application covers this exact hostname/path, then verify the
  Worker's audience and team domain match the JWT issuer and audience.
- **Access login succeeds but the room says membership is required:** authenticate
  as the exact invited email. External identities cannot create rooms; ask a
  current member to invite that address. A Cloudflare employee may create a new
  room, but cannot take over a room another member already owns.
- **A message or response disappeared:** Glide checks `/get-messages` after an
  interrupted send. It restores an undelivered message to the composer or offers
  **Retry response** when the user turn persisted without an assistant reply.
- **A token stays unverified:** confirm that it can read at least one account or
  zone and that its resource scope includes the intended account. Replace it under
  **Connection → Change** if those reads fail.
- **The UI remains on "Loading room...":** use the full Worker URL from `npm run
  dev`. Also verify that the Worker has built assets and inspect the browser's
  WebSocket request.

For structured event meanings, log queries, and the incident workflow, see
[Troubleshooting & observability](./troubleshooting.md).
